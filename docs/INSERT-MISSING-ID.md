# Twelve INSERTs that cannot work against a real database

## The finding

Every table in `database/turso/001_core.sql` declares its primary key as:

    id TEXT PRIMARY KEY

with **no DEFAULT**. That is not an oversight in the translation — it is
deliberate. `scripts/pg2turso.py` strips the source schema's
`DEFAULT gen_random_uuid()`:

    def strip_defaults(expr):
        """Remove Postgres-only DEFAULT expressions from a column definition."""
        expr = re.sub(r"DEFAULT\s+gen_random_uuid\(\)", "", expr, flags=re.I)
        expr = re.sub(r"DEFAULT\s+uuid_generate_v4\(\)", "", expr, flags=re.I)
        expr = re.sub(r"DEFAULT\s+nextval\([^)]*\)", "", expr, flags=re.I)

`gen_random_uuid()` is a Postgres function. It does not exist in SQLite. Keeping
it would produce a schema that could not be created at all, which is the right
call — but the consequence has to be handled on the other side, and for a long
time it was not.

**The id therefore has to be generated by the application.** These twelve
INSERT statements did not do that. Against a real database, every one of them
fails on the NOT NULL constraint of the primary key.

## Why the id is generated in JavaScript, not by a schema DEFAULT

This project reaches **both** libSQL and Postgres through one data path
(`netlify/functions/utils/database-service.js`). There is no single default
expression that is valid on both:

- `gen_random_uuid()` — Postgres 13+. Not in SQLite.
- `lower(hex(randomblob(16)))` — SQLite. Not in Postgres.

So the id is made in one place in JavaScript, where it means the same thing
either way:

    const DatabaseService = require('./utils/database-service');
    const params = [ DatabaseService.newId(), /* ... */ ];

`newId()` is `crypto.randomUUID()`. The ids are TEXT and opaque — nothing in this
codebase parses one, and nothing needs to.

## Why a test suite did not catch this sooner

Every one of these paths was mocked. The tests supplied a fake
`DatabaseService.query` that returned rows regardless of the SQL it was given,
so an INSERT with no id produced a row with an id, and the assertion passed.

That is the failure mode worth naming: **a fake that is more forgiving than the
database is worse than no fake**, because it converts a guaranteed production
failure into a green test. The fake in `tests/setup.js` now applies writes
rather than just answering them, which is what surfaced this class of bug.

The remaining gap is that it does not enforce column constraints. It should —
see the next section.

## The gate that should exist

`scripts/pg2turso.py` knows which tables have a `TEXT PRIMARY KEY` with no
default. Any INSERT into one of them that omits `id` is a guaranteed runtime
failure. That is mechanically checkable, and it is not currently checked
anywhere. It belongs next to the other build gates in `ci/`:

    for each CREATE TABLE in database/turso/*.sql:
        if the id column is TEXT and has no DEFAULT:
            every `INSERT INTO <table> (` in netlify/functions/ must list `id`

Until that exists, the seventeen statements above are the whole list, and a
seventeenth can be added without anyone noticing.
